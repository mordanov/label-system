## Задача

Разработай локально работающую систему учёта продуктов (например, для домашней морозилки/кладовки) с печатью этикеток на BLE-термопринтере MXW01. Система должна разворачиваться через Docker Compose.

## Общая архитектура

Ключевое ограничение: принтер MXW01 подключается по Bluetooth LE, а Docker Desktop на macOS работает внутри Linux-виртуалки без доступа к Bluetooth-адаптеру хоста. Поэтому:

- **`db`** (PostgreSQL), **`backend`** (Python 3.13) и **`frontend`** (React) — контейнеры в `docker-compose.yml`.
- **`print-service`** — отдельный НЕконтейнеризованный Python-процесс, который запускается нативно на macOS-хосте (вне Docker) и общается с принтером через BLE-библиотеку `bleak` (на macOS она использует CoreBluetooth напрямую, поэтому это единственный надёжный вариант). Он поднимает простой локальный HTTP-сервер (например, FastAPI на порту 9100) с одним эндпоинтом типа `POST /print`.
- Backend-контейнер обращается к print-service по HTTP через `http://host.docker.internal:9100` (адрес и порт вынести в `.env`, не хардкодить).
- Сделай print-service отдельной папкой в репозитории (`print-service/`) с собственным `requirements.txt` и README, как его запускать на macOS (venv + `python main.py`, опционально пример `launchd`-plist для автозапуска в фоне).

За основу протокола печати MXW01 возьми логику из открытого проекта `PinThePenguinOne/MXW01_Thermal-Printer-Tool` (Python + bleak, ширина ленты 384px, конвертация изображения в 1-бит). Изучи его реализацию и адаптируй под сервис с HTTP-эндпоинтом вместо CLI.

## Модель данных (PostgreSQL)

Таблица `products`:
- `id` — internal PK (serial/uuid)
- `inventory_number` — CHAR(4), сквозная нумерация с 0001, при достижении 9999 сброс на 0001. Генерация номера должна быть атомарной и защищённой от гонок (отдельная таблица-счётчик с `SELECT ... FOR UPDATE` в транзакции, либо аналог через advisory lock).
- `name` — текст, название продукта
- `icon_filename` — имя файла иконки из галереи
- `created_at` — дата создания (используется при печати)
- `is_deleted` — boolean, soft delete (по умолчанию false)
- `deleted_at` — timestamp, nullable
- `deleted_by` — имя пользователя, который вычеркнул (nullable)

Важно: при повторной печати этикетки для существующего продукта **инвентарный номер переиспользуется**, новый не генерируется — это тот же физический продукт, просто перепечатывается утерянная этикетка.

Соединение с БД настраивается только через переменные окружения (`DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`), без хардкода — база в будущем может переехать на другой хост. Используй Alembic для миграций.

## Галерея иконок

- В репозитории — папка `assets/icons/` с предзаполненными чёрно-белыми PNG-иконками (заглушки на первое время можно сгенерировать/оставить пустыми — их заменит пользователь).
- Папка копируется в образ backend-контейнера через `COPY` в Dockerfile (пересборка образа при добавлении новых иконок — это ожидаемое поведение).
- Backend отдаёт список доступных иконок (имя файла + сам файл/превью) фронтенду через API.
- При создании продукта пользователь выбирает одну иконку из галереи, она сохраняется как `icon_filename`.

## Формирование этикетки

Print-service при печати получает от backend: `inventory_number`, `name`, `created_at`, `icon_filename`, а также сам файл иконки (или общий доступ к папке с иконками — реши сам, что удобнее: либо тоже смонтировать/скопировать иконки в print-service, либо backend передаёт байты картинки в запросе).

Макет этикетки (ширина под 384px принтера):
- Иконка (glyph) продукта
- Название продукта
- Инвентарный номер (крупно, в формате `#0001`)
- Дата создания

Рендерить через Pillow: собрать PIL-изображение нужной ширины, наложить текст и иконку, привести к чёрно-белому 1-бит (Floyd–Steinberg дизеринг для иконки, если она не строго ч/б), передать в протокол MXW01.

## Backend (Python 3.13)

Рекомендуемый стек: FastAPI + SQLAlchemy (async) + Alembic + httpx (для похода в print-service).

Эндпоинты:
- `POST /products` — создать продукт (name, icon_filename) → генерирует inventory_number, created_at, сохраняет в БД, вызывает print-service, возвращает созданную запись.
- `POST /products/{id}/reprint` — повторно распечатать этикетку для существующего активного продукта (тот же inventory_number).
- `GET /products` — список продуктов с фильтром по `name` (частичное совпадение, регистронезависимо) и опциональным включением/исключением вычеркнутых.
- `POST /products/{id}/delete` — soft delete: выставляет `is_deleted=true`, `deleted_at=now()`, `deleted_by=<текущий пользователь>`. Без физического удаления строки.
- `GET /icons` — список доступных иконок.

Аутентификация: HTTP Basic Auth. Два пользователя, логины и пароли задаются переменными окружения (например `APP_USER_1`/`APP_PASS_1`, `APP_USER_2`/`APP_PASS_2`). Роли не нужны — оба пользователя равноправны, но имя пользователя, выполнившего soft delete, должно сохраняться в `deleted_by` для истории изменений.

## Frontend (React)

- Форма создания продукта: название + выбор иконки из галереи (превью картинок) → кнопка «Добавить и напечатать».
- Таблица продуктов: инвентарный номер, название, иконка, дата, статус (активен / вычеркнут — с указанием кем и когда, если вычеркнут).
- Поиск/фильтр по названию (live-фильтр или кнопка «Найти»).
- Кнопка «Печать» / «Перепечатать этикетку» у каждой активной строки.
- Кнопка «Вычеркнуть» у активных строк (с подтверждением), после чего строка помечается как вычеркнутая, но остаётся видимой в списке (не исчезает) с историей — кто и когда.
- Basic Auth: логин через стандартный браузерный диалог (или простую форму, дублирующую Basic Auth заголовок) — как удобнее реализовать с учётом бэкенда.

## Docker Compose

Сервисы: `db` (postgres, с volume для персистентности данных), `backend`, `frontend`. Все настройки — через `.env` в корне проекта, включая:
```
DB_HOST=db
DB_PORT=5432
DB_USER=...
DB_PASSWORD=...
DB_NAME=...
APP_USER_1=...
APP_PASS_1=...
APP_USER_2=...
APP_PASS_2=...
PRINT_SERVICE_URL=http://host.docker.internal:9100
PRINTER_BLE_ADDRESS=...   # используется только print-service'ом, вне Docker
```

Добавь `.env.example` с заполненными плейсхолдерами и явный комментарий в README, что `print-service` запускается отдельно на хосте (не через `docker-compose up`), с инструкцией по установке зависимостей и запуску.

## Скрипты запуска/остановки

Добавь в `scripts/` два shell-скрипта (bash, для macOS), которые управляют всей системой целиком одной командой:

- `scripts/start.sh` — поднимает `docker-compose up -d` (db, backend, frontend) и параллельно запускает `print-service` в фоне на хосте (например, через `nohup ... &` с сохранением PID в `.print-service.pid`, и логом в `print-service/print-service.log`). Скрипт должен проверять, что виртуальное окружение print-service создано и зависимости установлены — если нет, установить перед запуском.
- `scripts/stop.sh` — останавливает print-service по сохранённому PID и делает `docker-compose down`.

Оба скрипта должны быть идемпотентными (повторный запуск `start.sh`, когда всё уже работает, или `stop.sh`, когда всё уже остановлено, не должен падать с ошибкой) и выводить понятный статус в консоль.
