# Промпт для Claude Code: поддержка Windows для скриптов запуска/остановки

Контекст: уже есть система учёта продуктов с печатью этикеток (Docker Compose: `db`, `backend`, `frontend` + нативный `print-service`, использующий `bleak` для BLE-связи с принтером MXW01). Изначально скрипты управления (`scripts/start.sh`, `scripts/stop.sh`) написаны под macOS (bash). Задача — добавить поддержку Windows, не трогая основную бизнес-логику backend/frontend/print-service.

## Что нужно сделать

1. **Добавить `scripts/start.ps1` и `scripts/stop.ps1`** (PowerShell), эквивалентные по поведению существующим bash-скриптам:
   - `start.ps1`:
     - поднимает `docker-compose up -d` (db, backend, frontend);
     - проверяет, создано ли виртуальное окружение для `print-service` (venv), при отсутствии — создаёт и ставит зависимости из `print-service/requirements.txt`;
     - запускает `print-service` в фоне (например, через `Start-Process` с сохранением PID в `.print-service.pid` в корне проекта, лог — в `print-service/print-service.log`);
     - идемпотентен: повторный запуск при уже работающей системе не должен падать с ошибкой, а должен сообщать, что сервисы уже запущены.
   - `stop.ps1`:
     - останавливает `print-service` по сохранённому PID (если процесс жив);
     - выполняет `docker-compose down`;
     - идемпотентен: повторный вызов при уже остановленной системе не должен падать с ошибкой.

2. **Проверить `bleak`-логику в `print-service` на предмет платформенных допущений.** На Windows `bleak` использует WinRT-бэкенд вместо CoreBluetooth (macOS). Убедиться, что в коде нет прямых вызовов или зависимостей, специфичных для macOS-бэкенда (обычно их нет, так как `bleak` абстрагирует бэкенд сам, но нужно явно это проверить и, если были macOS-специфичные workaround'ы, вынести их под платформенную проверку `platform.system()`).

3. **Обновить README:**
   - Указать, что на Windows скрипты `start.ps1` / `stop.ps1` запускаются из PowerShell (`./scripts/start.ps1`), возможно потребуется разрешить выполнение скриптов (`Set-ExecutionPolicy` для текущего пользователя — упомянуть команду).
   - Уточнить, что `host.docker.internal` в Docker Desktop для Windows работает аналогично macOS, дополнительной настройки не требуется.
   - Явно указать, что ограничение по BLE в Docker-контейнерах на Windows такое же, как на macOS (Docker Desktop работает через WSL2-виртуалку без доступа к Bluetooth-адаптеру хоста), поэтому `print-service` в обоих случаях остаётся нативным процессом на хосте, а не контейнером.
   - Указать разницу в автозапуске: на macOS — `launchd` (уже описан), на Windows — через Планировщик заданий (Task Scheduler) с задачей, запускающей `start.ps1`; дать краткий пример.

4. **Не менять** порты, переменные окружения, структуру `.env`, докер-компоуз файлы и протокол общения backend ↔ print-service — задача только про кроссплатформенность скриптов управления и проверку `bleak`.

5. Придерживайся тех же практик, что и в основном проекте: если в репозитории уже используется плагин **ponytail** — работай в его режиме (минимально достаточное решение, без лишних абстракций). Так же обновляй `PROGRESS.md` и делай `git commit` после каждого завершённого шага (добавлены start.ps1/stop.ps1, обновлено README, проверена bleak-логика).
